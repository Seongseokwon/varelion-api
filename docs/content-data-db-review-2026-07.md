# 콘텐츠 데이터(몬스터/전투/캐릭터) DB 설계 점검 (2026-07)

> 작성 2026-07-17 · 근거: `prisma/schema.prisma` + `varelion-web/src/data/*.ts` + `varelion-design/docs/game-design/`(`ITEMIZATION.md`, `MONSTER_BIBLE.md`, `IDLE_DUNGEON.md`) 교차 검토
> `docs/backend-review-2026-07.md`(인프라/코드 품질 점검)와 별개로, "몬스터/전투/캐릭터 정보를 관리하기에 DB 설계가 적절한가"만 따로 점검한 기록.
> 지금 당장 코드를 고치라는 문서가 아니라, **다음에 아이템 시스템(`ITEMIZATION.md`) 구현에 들어가기 전에 결정해야 할 것**을 남겨두는 문서.

## 결론 요약

- 지금 DB에 몬스터/캐릭터/전투 "정의" 테이블이 없는 것은 **의도된 설계이고 지금 시점엔 맞다.** 실시간 클라이언트 시뮬레이션 콘텐츠라 서버 왕복이 오히려 안 맞는다.
- 서버로 실제로 넘어오는 콘텐츠 식별자는 `job`(enum 문자열) 하나뿐이고, 몬스터 단위 정보는 전혀 없다(킬 수는 항상 집계값). 지금 기능 범위(리더보드/세이브/부정 제출 방지)엔 충분하다.
- **다음 로드맵인 장비/유물 시스템(`ITEMIZATION.md`, 설계 완료·구현 전)이 기존 `GameSave.data` JSONB 경로를 그대로 타도록 설계돼 있는데, 이 경로에 두 가지 공백이 있다** — 아래 "발견 사항" 참고. 저장 자체는 마이그레이션 없이 가능하지만, 무결성 검증과 성장형 컬렉션 처리 방식은 미리 정하고 가는 게 좋다.
- 몬스터 도감(처치 기록)·방치 던전의 서버 시간 계산은 지금 걱정할 필요 없음(아래 "확인 사항" 참고).

---

## 1. 현재 상태 — 콘텐츠 테이블 없음 (의도된 설계)

`prisma/schema.prisma`엔 Monster/Job/Weapon 정의 테이블이 전혀 없다. 몬스터(`varelion-web/src/data/monsters.ts`, 4종), 직업 트리(`jobs.ts`, tier 0~5), 무기·패시브(`weapons.ts`/`passives.ts`)는 전부 프론트 정적 파일이다.

이건 버그가 아니라 맞는 선택이다 — 60fps 실시간 시뮬레이션이 매 프레임 몬스터 스탯을 서버에 물어볼 수는 없다. `BACKEND_DESIGN.md` §1의 원래 방침("게임플레이 자체는 클라이언트, 백엔드는 판이 끝난 뒤의 결과와 계정 데이터만") 그대로다.

## 2. 서버로 넘어오는 콘텐츠 접점

- `job`: `CreateRunDto`의 `VALID_JOB_IDS`(`src/config/game-balance.json`)로 검증되는 enum 문자열. 리더보드 표시용으로만 쓰임(스탯 자체엔 영향 없음).
- 몬스터: 서버에 전혀 넘어오지 않음. `BattleEvent`의 `kills` 타입 이벤트는 `{killsDelta, goldDelta}` 집계값만 가짐 — "어떤 몬스터를 몇 마리 잡았는지"는 어디에도 기록되지 않음.

지금 기능 범위(리더보드·세이브 동기화·부정 제출 방지)엔 이 정도로 충분하다.

## 3. 발견 사항 — 다음 확장(장비·유물)이 이 경계를 깬다

`ITEMIZATION.md`(버전 0.2, 상태: 설계 문서/전체 미구현)의 결정 로그 1번:

> "장비는 런 중 드랍 → 즉시 계정 영구 귀속 + 즉시 전투 반영. 골드처럼 `gameOver()` 시점까지 정산을 미루지 않는다 — 습득 즉시 `save.inventory`/`save.equipped`에 반영하고 `writeSave()`를 호출한다."

이 설계는 기존 `GameSave.data` JSONB 경로(`src/saves/saves.service.ts`)를 그대로 타도록 되어 있어서, **저장 자체는 마이그레이션 없이 지금 스키마로 가능하다**(`data` 컬럼이 원래 "구조가 자주 바뀔 값"을 담으려고 만든 필드라 딱 맞음). 다만 이 경로를 실제로 타보면 두 가지가 걸린다.

### 3.1 무결성 검증 공백

`SavesService.assertPlausibleIncrease`(`src/saves/saves.service.ts:131-153`)는 `metaLevel`/`metaXp`/`gold` 세 필드만 검증한다. `validateKnownFields`도 이 셋만 뽑아내고, 나머지는 전부 `data` JSONB로 그대로 통과한다(`@IsObject()`만 걸려있어 형태 제약이 사실상 없음).

지금은 검증할 만한 "파워"가 이 세 값뿐이라 문제가 없었는데, 장비가 새 파워 축으로 들어오는 순간 — 브라우저 콘솔에서 `save.inventory`에 전설 등급 아이템을 직접 채워 `PUT /saves/me`를 보내도 서버가 걸러낼 방법이 전혀 없다. `Run`/`BattleSession`에 있던 "제출값을 뭔가와 대조한다"는 원칙이 `GameSave`에는 애초에 없다.

### 3.2 JSONB 통짜 덮어쓰기와 안 맞는 성장형 컬렉션

`save.inventory: EquipmentItem[]`는 "전부 영구 보관"(삭제 없음)이라 계정 수명 내내 계속 자라는 배열인데, 지금 `PUT /saves/me`는 매번 `data` 전체를 통째로 교체하는 낙관적 잠금 방식이다(`saves.service.ts:74-89`).

`seenJobs`, `stagesCleared`처럼 크기가 사실상 고정인 필드에는 이 방식이 맞지만, 개별 아이템이 `id`(uuid)까지 갖고 계속 누적되는 컬렉션은 원래 "행 하나당 아이템 하나"인 관계형 테이블에 더 맞는 모양이다. 베테랑 계정의 인벤토리가 수백 개로 늘어나면 세이브를 저장할 때마다 그 전체를 왕복시키는 셈이 된다.

## 4. 확인 사항 — 지금 걱정할 필요 없는 것

- **몬스터 처치 도감**: 로비 하단 "도감" 탭은 아직 `ComingSoonPanel` 플레이스홀더뿐이고, 실제로 설계된 도감은 유물 해금 기록(`save.relicsUnlocked`, `ITEMIZATION.md` §4.4)이지 몬스터 처치 도감은 설계 문서 자체가 없다. 유물 해금 기록은 이미 JSONB 배열로 커버되는 성격(플래그성 기록, 삭제 없음, 항목 수가 유물 종류 수만큼으로 유한)이라 3.2절 문제와는 다르다.
- **방치 던전(`IDLE_DUNGEON.md`)의 서버 시간 계산**: 문서에서 "완전한 오프라인 진행은 다루지 않는다"고 명시(§0) — 탭을 열어둔 상태의 오토플레이만 다룸. 서버가 경과 시간을 계산해 보상을 주는 방식이 아니라서 관련 스키마 고민은 필요 없음.

## 5. 아이템 시스템 착수 전 결정 필요 사항

지금 당장 고칠 건 없다 — 아이템 시스템 자체가 "전체 미구현" 상태이기 때문이다. 다만 **`ITEMIZATION.md` 구현에 들어가기 전에** 아래 중 하나를 결정하고 가는 것을 추천한다.

- [ ] **옵션 A**: `GameSave.data`에 `inventory`가 들어올 때 서버가 최소한의 상식 검증을 추가한다(예: 등급별 분포·개수가 플레이 시간 대비 말이 되는지, `Run`의 물리적 상식 검증과 비슷한 수준의 "명백한 조작 차단"). 구현 부담이 적고 기존 패턴(JSONB) 유지.
- [ ] **옵션 B**: 처음부터 `Equipment`를 별도 테이블(`userId`, `id` uuid, `slot`, `rarity`, `affixes` jsonb, `foundAt`, `equipped` bool)로 분리하고, 드랍 자체를 서버가 발급하는 구조로 간다(`battle-sessions`가 킬/골드를 이벤트 로그로 대조검증하듯, 장비 드랍도 세션 이벤트의 일종으로 다룰 수 있음). 다만 이건 "클라이언트가 굴리고 서버는 사후 검증"이라는 지금 프로젝트 전체 철학과는 다른 방향이라 설계 범위가 커짐.
- [ ] 위 결정과 별개로, 결정이 늦어져도 무방하다면 **옵션 C(현행 유지)**: 지금처럼 무검증 JSONB로 일단 출시하고, 실제로 조작 사례가 관측되면 그때 옵션 A/B 중 하나로 전환. 리더보드처럼 "신뢰도 문제이지 절대 방지가 목적이 아니다"라는 프로젝트 기존 방침과도 일관됨 — 다만 이 경우 아이템 시스템은 리더보드 순위에 영향을 주지 않는 것으로 (역시) 결정해둬야 뒤탈이 없음(현재 리더보드는 kills/survivalTime/metaLevel만 반영하므로 장비가 "전투력"에만 영향을 주고 리더보드 산식엔 안 들어가면 이 리스크의 심각도가 낮아짐 — 확인 필요).

세 옵션 다 지금 구현하라는 게 아니라, 아이템 시스템 착수 시점에 이 문서를 다시 펴서 하나를 고르고 시작하자는 메모다.
