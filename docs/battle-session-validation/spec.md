# battle-session-validation — 전투 데이터 서버 검증 명세서

> 작성 2026-07-14 · 근거: 사용자 제안 문서("전투 데이터 저장 방식 개선 방향"), `docs/BACKEND_DESIGN.md` §7, `docs/archive/save-sync/`, `docs/archive/leaderboard-sort/`
> 상태: **초안 (승인 대기)**

## 결정 이력 (사용자 확정)

| 쟁점 | 결정 |
|------|------|
| 검증 방식 전환 | 기존 상식 검증(킬/초 상한 + 제출 간격)만으로는 부족하다고 보고, 세션+이벤트로그+대조검증 방식으로 **전면 전환**. `BACKEND_DESIGN.md` §7의 "리플레이 검증·서버 시뮬레이션은 과잉" 결정은 이 기능 범위에서 **재검토·대체**됨(단, 아래 범위에서 보듯 완전한 리플레이/시뮬레이션은 여전히 하지 않음 — "이벤트 로그 대조"와 "리플레이"는 다른 수준임, 아래 개요 참고) |
| 계정 세이브 동기화(save-sync) | 이미 구현 완료된 기능. 이번 스펙 범위에 **재검토 포함** — 세션 기반 방식과 함께 쓰였을 때 어긋나는 지점이 있는지 점검(아래 FR-13, 기존 코드와의 접점 참고). 세이브 동기화 자체의 재구현은 아님 |
| 이벤트 전송 방식 | **유형별 분리** — 저빈도 이벤트(레벨업, 스테이지 클리어)는 발생 즉시 개별 전송, 고빈도 이벤트(몬스터 처치)는 5~10초 주기로 누적치를 배치 전송 |
| 검증 실패 시 처리 | 사용자 원안대로 **리더보드 반영 보류/플래그 처리** — 제출 자체를 거부(400)하지 않음 (기존 `runs.service.ts`의 물리적 상식 검증은 그대로 유지, 이번 대조검증은 그 위에 추가되는 별도 판정) |

## 개요

현재 전투 로직은 전부 클라이언트에서 계산되고, 서버는 판 종료 시 최종 결과 1회만 받아 물리적 상식 검증(킬/초 상한, 제출 간격)만 수행한다. 이 기능은 전투 시작 시 서버에 세션을 생성하고, 진행 중 주요 이벤트(킬 누적치, 레벨업, 스테이지 클리어)를 서버로 전송하며, 종료 시 최종 결과를 그 이벤트 로그와 대조해 리더보드 신뢰도를 높인다. 서버가 게임을 재시뮬레이션하는 것은 아니며, "클라이언트가 실시간으로 보고한 값들의 합이 최종 제출값과 일치하는가"를 확인하는 수준의 대조 검증이다.

## 범위

**포함**
- 백엔드: 전투 세션 모델(`BattleSession`) + 시작 API, 이벤트 수신 API(킬 배치 / 레벨업 / 스테이지 클리어), 기존 `POST /runs` 제출 시 세션 이벤트 로그와의 대조검증 및 판정 결과 저장
- 프론트: 판 시작 시 세션 생성 요청, 진행 중 이벤트 전송(유형별 분리 — 즉시/배치), 네트워크 실패 시 재시도 큐, 판 종료 제출에 세션 id 포함
- 대조검증 실패(불일치) 시 리더보드 조회에서 제외되도록 플래그 반영(하드 거부 아님)
- save-sync와의 상호작용 재검토(세션/이벤트 API 도입이 세이브 업로드 타이밍·검증에 영향을 주는지 확인, 필요 시 최소 조정 범위만 이 기능에 포함)

**명시적으로 제외**
- 서버 측 게임 로직 재시뮬레이션(완전한 리플레이 검증) — 사용자 원 로드맵에서도 별도 항목(5번, Post-MVP)으로 분리되어 있음
- 결정론적 시드 기반 RNG 도입(`Math.random()` 전면 교체) — 세션이 시작 시각은 기록하지만, 클라이언트 RNG를 시드로 고정하는 리팩터는 이 범위 밖(아래 미해결 사항 참고)
- 이상 탐지/치팅 패턴 고도화(로드맵 5번, Post-MVP) — 이번 범위는 "불일치 플래그"까지만, 통계적 이상탐지·자동 제재 규칙은 다루지 않음
- 아이템 획득 이벤트 — 현재 게임에 장비/유물 시스템이 없고(`MEMORY.md` "기획 대비 아직 없는 것"), 물약 픽업은 리더보드 필드(킬/레벨/골드)에 직접 영향이 없어 검증 대상에서 제외. 골드는 킬 이벤트 배치에 포함되는 값으로 다룸(아래 FR-3)
- 데일리 챌린지, 리플레이 재생 UI, 통계 대시보드 — 사용자 원 문서의 "기대 효과"에 언급된 미래 항목이며 이번 범위 밖
- 무한 모드/스테이지 모드 외 신규 게임 모드 추가 — 없음(기존 두 모드 그대로)

## 사용자 시나리오

1. 로그인한 플레이어가 판을 시작하면, 서버에 전투 세션이 생성되고 이후 진행 중 이벤트가 그 세션에 누적된다. 플레이어는 이 과정을 인지하지 못한다(기존처럼 즉시 플레이 시작).
2. 플레이어가 레벨업하거나 스테이지를 클리어하면, 해당 이벤트가 즉시 서버에 기록된다.
3. 플레이어가 몬스터를 처치하면, 처치 수와 획득 골드가 5~10초 주기로 누적되어 서버에 배치 전송된다.
4. 판이 끝나 결과가 제출되면, 서버는 해당 세션에 쌓인 이벤트 로그 합계와 제출된 최종 결과(킬/레벨/골드)를 대조한다. 일치하면 기존과 동일하게 리더보드에 반영된다.
5. 네트워크가 불안정해 일부 이벤트 전송이 실패해도, 클라이언트는 큐에 남겨 뒀다가 재시도하며 게임 진행 자체는 막히지 않는다.
6. 대조 결과가 크게 어긋나면(예: 이벤트 로그에 없는 킬수가 제출됨) 해당 판은 저장은 되지만 리더보드 조회에서 제외된다. 플레이어의 게임 진행(메타 레벨/골드 적립)은 영향받지 않는다(사용자 원 문서 결정 — 검증은 리더보드 신뢰도 문제이지 플레이어 처벌 문제가 아님, 아래 미해결 사항도 참고).
7. 게스트(비로그인) 플레이는 세션/이벤트 API를 전혀 호출하지 않는다(기존 `runs`/`saves` 게스트 배제 관례와 동일) — 리더보드에 반영되지 않는 판이므로 검증 대상이 아니다.
8. 브라우저가 갑자기 종료되어 세션이 끝까지 종료되지 않아도, 그때까지 누적된 이벤트 로그는 서버에 남아 향후 통계·이상탐지(Post-MVP)의 기초 자료가 된다.

## 기능 요구사항

### 백엔드 (varelion-api)

- **FR-1**: 로그인 사용자가 판을 시작하면 서버에 전투 세션이 생성된다. 세션은 소유 유저, 시작 시각, 진행 중(active)/종료(finalized) 상태를 가진다.
- **FR-2**: 세션 생성 API는 인증을 요구하며, 생성된 세션의 식별자를 반환한다.
- **FR-3**: 킬 배치 이벤트 API(인증 필요)는 `{sessionId, killsDelta, goldDelta}`를 받아 해당 세션에 누적한다. 이미 종료(finalized)된 세션이나 본인 소유가 아닌 세션에 대한 요청은 거부된다.
- **FR-4**: 레벨업 이벤트 API(인증 필요)는 `{sessionId, level}`을 받아 해당 세션에 기록한다(도달한 세션 레벨의 최댓값을 유지하면 됨 — 사용자 시나리오 2). 세션 상태 제약은 FR-3과 동일.
- **FR-5**: 스테이지 클리어 이벤트 API(인증 필요)는 `{sessionId, stageId}`를 받아 해당 세션에 기록한다. 세션 상태 제약은 FR-3과 동일.
- **FR-6**: 기존 `POST /runs`(판 결과 제출)에 `sessionId`가 함께 전달되면, 서버는 그 세션의 누적 이벤트(킬 합계·최고 레벨·골드 합계)와 제출된 `kills`/`level`/`goldEarned`를 대조한다. 대조 후 세션은 종료(finalized) 상태로 바뀌며 이후 그 세션으로의 이벤트 전송(FR-3~5)은 거부된다.
- **FR-7**: 대조 결과 불일치(제출값이 이벤트 로그 합계로 설명되지 않는 수준)가 있으면 해당 `Run`은 저장되지만 검증 실패로 표시되어, 리더보드 조회(`GET /leaderboard`, `GET /leaderboard/me`)에서 제외된다.
- **FR-8**: `sessionId` 없이 제출되거나, 존재하지 않는/이미 종료된 세션 id로 제출되면 대조검증은 "세션 없음"으로 표시되어 FR-7과 동일하게 리더보드에서 제외된다(기존 물리적 상식 검증은 세션 유무와 무관하게 그대로 통과해야 저장됨 — 두 검증은 독립적으로 작동).
- **FR-9**: 기존 `runs.service.ts`의 물리적 상식 검증(킬/초 상한, 제출 간격)은 그대로 유지된다 — 이번 기능은 그 위에 대조검증을 추가하는 것이지 대체가 아니다.
- **FR-10**: 인증 없는 세션/이벤트 API 요청은 401을 반환한다.
- **FR-11**: 종료되지 않은 채 일정 시간(예: 세션 상한 시간) 이상 지난 세션은 별도 처리 없이 방치된다 — 통계용 원시 데이터로만 보존되며 리더보드에는 애초에 영향이 없다(제출되지 않았으므로).

### 프론트 (src/)

- **FR-12**: 로그인 상태에서 판을 시작하면(`newRun()` 경로) 세션 생성을 요청하고 반환된 세션 id를 세션 상태(`run`)에 보관한다. 게스트는 이 요청을 하지 않는다.
- **FR-13**: 세션 생성이 실패(네트워크 오류 등)해도 게임 진행은 막히지 않는다 — 이 경우 세션 id 없이 진행하며, 판 종료 제출은 FR-8에 따라 자동으로 리더보드 제외 대상이 된다(하드 실패 아님, 조용한 열화).
- **FR-14**: 레벨업 발생 시(`flow.js`의 `levelUp()` 경로) 즉시 레벨업 이벤트를 전송한다.
- **FR-15**: 스테이지 클리어 판정 시(`gameOver(true)`이고 `run.stage`가 있을 때) 즉시 스테이지 클리어 이벤트를 전송한다.
- **FR-16**: 몬스터 처치가 발생하면(`enemies.js`의 킬 처리 경로) 처치 수·골드 획득을 세션 로컬에 누적하고, 5~10초 주기로 누적된 값을 배치 전송한 뒤 누적치를 초기화한다.
- **FR-17**: 이벤트 전송(킬 배치/레벨업/스테이지클리어)이 네트워크 실패로 실패하면 클라이언트 큐에 남아 다음 전송 시도(다음 배치 주기 또는 판 종료 시)에 함께 재시도된다. 재시도로도 실패한 이벤트는 판 종료 제출까지 유실될 수 있으며, 이 경우 서버 대조검증에서 불일치로 처리될 수 있다(사용자 시나리오 5·6 — 게임 진행 자체는 막지 않는다는 원칙이 우선).
- **FR-18**: 판 종료 제출(`submitRunResult()`)은 보관 중인 세션 id를 `POST /runs` 요청에 함께 보낸다. 세션 id가 없으면(FR-13) 기존처럼 세션 id 없이 제출한다.
- **FR-19**: 무한 모드 이탈(라우트 이탈 등 "정산 없이 폐기"되는 기존 경로)로 세션이 끝까지 종료되지 않는 경우, 클라이언트는 별도 세션 종료 신호를 보내지 않는다(FR-11로 서버가 방치 처리).

## 비기능 요구사항

- **성능**: 킬 배치 전송은 5~10초 주기로 상한되어, 진행 중 서버 요청 빈도가 무한 모드 장시간 플레이에서도 세이브 동기화(3초 디바운스)와 비슷한 수준 이하로 유지된다. rAF 루프나 화면 전이를 블로킹하는 동기 네트워크 대기는 없다(기존 api.js 비동기 관례 유지).
- **보안**: 세션/이벤트 API는 모두 JWT 인증 필수. 세션 소유자 검증(FR-3~5의 "본인 소유가 아닌 세션 거부")으로 다른 유저 세션에 이벤트를 주입할 수 없다.
- **장애 허용**: 세션 생성·이벤트 전송·대조검증 중 어떤 단계가 실패해도 게임 플레이와 판 종료 흐름 자체는 기존과 동일하게 동작한다(FR-13, FR-17) — 이 기능은 "있으면 신뢰도가 올라가는" 부가 계층이지 필수 경로가 아니다.
- **호환성**: `sessionId`가 없는 기존 클라이언트(또는 배포 과도기)의 `POST /runs` 요청도 계속 동작한다(FR-8) — 리더보드 제외라는 열화만 있을 뿐 요청 자체는 거부되지 않는다.

## 엣지 케이스 및 에러 처리

| 상황 | 기대 동작 |
|------|-----------|
| 세션 생성 실패(오프라인 등) | 세션 id 없이 게임 진행, 판 종료 시 리더보드 제외 대상으로 제출(FR-13) |
| 킬 배치 전송 중 네트워크 끊김 | 클라이언트 큐 보관 후 재시도, 최종 실패 시 대조 불일치 가능(FR-17) |
| 이미 종료(finalized)된 세션에 이벤트 전송 시도 | 거부(FR-3~5 세션 상태 제약) — 판 종료 후 지연 도착한 이벤트가 다음 판에 잘못 합산되는 것을 방지 |
| 다른 유저의 세션 id로 이벤트 전송 시도 | 거부(FR-3~5) |
| `sessionId` 없이 `POST /runs` 제출(구 클라이언트·세션 생성 실패) | 물리적 상식 검증은 정상 통과 시 저장되나, 대조검증 "세션 없음"으로 리더보드 제외(FR-8) |
| 대조 불일치(예: 신고된 킬수가 이벤트 로그 합계를 크게 초과) | `Run` 저장은 유지, 리더보드 조회에서만 제외(FR-7) — 메타 레벨/골드 등 세이브 반영은 별개 경로(`gameOver()`)라 영향 없음 |
| 정상 플레이인데 이벤트 몇 건이 재시도로도 유실(순간적 네트워크 단절) | 대조 허용 오차 범위 내면 통과 — 오탐 방지를 위한 여유 마진 필요(구체적 수치는 계획 단계 또는 구현 중 튜닝, save-sync FR-7 상식 검증의 "여유 마진" 선례를 따름) |
| 게스트 플레이 | 세션/이벤트 API 호출 없음, 기존과 동일(FR-12) |
| 세션 생성 후 판을 끝까지 하지 않고 이탈(무한 모드 라우트 이탈) | 세션은 미종료 상태로 방치, 리더보드 영향 없음(FR-11, FR-19) |

## 미해결 사항

- **대조 불일치 허용 오차의 구체적 수치**: "여유 마진"이 필요하다는 원칙은 확정했으나(엣지 케이스 표), 정확한 임계값(예: 킬수 몇 % 초과까지 허용)은 계획 단계 또는 구현 중 튜닝 항목으로 남김
- **시드 기반 RNG(결정론적 재생) 도입 여부**: 사용자 원 문서는 세션 생성 시 "시드값 기록"을 언급했으나, 현재 게임은 `Math.random()`을 전역적으로 사용해 결정론적이지 않다. 이번 범위는 시드를 실제로 사용하는 RNG 리팩터를 포함하지 않는다(전면 제외로 명시). 세션에 시드 필드 자체를 지금 만들어 둘지(향후 대비, 사용처 없음) 아니면 아예 만들지 않을지는 계획 단계에서 결정
- **불일치 판정을 받은 유저에 대한 후속 조치**(계정 경고·제재 등): 사용자 시나리오 6에서 "플레이어 처벌 문제가 아님"으로 방향은 잡았으나, 반복 불일치 유저를 별도로 어떻게 다룰지는 로드맵 5번(이상탐지 고도화, Post-MVP)로 명시적으로 이월
- **이벤트 테이블 스키마 형태**: `BattleSession`에 집계 컬럼(킬 누적치·최고 레벨 등)만 둘지, 개별 이벤트를 별도 테이블에 로그로 남길지(사용자 원 문서의 "리플레이 대비" 기대효과에는 후자가 더 유리하나 이번 범위의 대조검증 자체는 집계값만으로 충분) — 계획 단계에서 트레이드오프 제시 후 결정
